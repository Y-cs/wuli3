# 扩展契约

看到一个接口时，先确认它的生效方式。接口存在不代表自动配置会自动找到它，更不代表远端协议已经接通。

## 四种扩展方式

| 方式 | 例子 | 应用要做什么 |
| --- | --- | --- |
| 纯 Java 组合 | ContextManager、RoutingEventPublisher | 自己创建、注册和控制生命周期 |
| 缺失时提供默认 Bean | AuthContextResolver、请求 ID 解析器 | 在扫描范围内声明 Bean，覆盖默认实现 |
| 收集多个 Bean | 错误映射、告警通知、事件 transport | 明确排序、命中规则和异常处理 |
| 协议适配 | ContextCodec、远程事件 transport | 完成编码、信任校验、投递、重试和观测 |

## 三个容易误判的边界

**注册接口不等于接通协议。** RemoteEventTransport 需要真实客户端、目标配置和失败策略；返回成功不能自动等同于可靠落库。

**自定义 Bean 不一定会被收集。** 例如自定义 ContextCodec 不会被默认 Web 自动配置自动加入所有传播器；需要按文档显式创建 ContextPropagator。

**关闭开关不等于补齐实现。** wuli3.permission.enforcement-enabled=false 可以关闭权限检查，但不能代替生产授权系统；缺少审计 store 也不能凭空得到持久审计。

## 写扩展时的验收问题

1. 扩展是在缺少默认实现时生效，还是与多个实现一起生效？
2. 输入来源是否已认证、校验和限长？
3. 失败时是拒绝启动、返回错误，还是降级为本地行为？
4. 是否需要幂等、重试、超时和关闭阶段排空？
5. 是否能用单元测试证明它没有泄露主体、凭据和内部错误？

按这些问题写契约测试，再进入[运行与运维](/capabilities/operations)配置关闭、日志和观测。
